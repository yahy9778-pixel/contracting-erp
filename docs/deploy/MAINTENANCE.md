# خطة الصيانة المستمرة

## يوميا (آلي، تتابعه بنظرة)

| ما يحدث | أين تتحقق |
| --- | --- |
| نسخة احتياطية الساعة 05:00 بتوقيت الرياض | `ls -lh /opt/contracting-erp/backups \| tail -3` |
| نسخ النسخة إلى التخزين الخارجي | `tail /home/deploy/rclone.log` |
| تحديثات الأمان لنظام التشغيل | تلقائية عبر `unattended-upgrades` |
| مراقبة `/api/health` | تنبيه من خدمة المراقبة عند التعطل |

إن لم يصلك تنبيه فالنظام يعمل. لا يلزم دخول يومي على الخادم.

## أسبوعيا (10 دقائق)

- [ ] `docker compose ps`: كل الخدمات Up والتطبيق healthy
- [ ] مساحة القرص أقل من 80%: `df -h /`
- [ ] أخطاء التطبيق في الأسبوع: `docker compose logs --since 168h app | grep -i error | tail -20`
- [ ] أحجام النسخ الاحتياطية متقاربة (نقص مفاجئ في الحجم يعني مشكلة)
- [ ] سجل التدقيق في **الإدارة ← سجل التدقيق**: لا عمليات غريبة، ولا محاولات دخول فاشلة كثيرة
- [ ] استهلاك Claude API في console.anthropic.com ضمن المتوقع

## شهريا (30 دقيقة)

- [ ] **تمرين استعادة**: استعد آخر نسخة على قاعدة تجريبية وتأكد أنها تفتح ([الطريقة](RUNBOOK.md#تمرين-الاستعادة))
- [ ] تحديث صور Docker الأساسية: `docker compose pull && docker compose up -d --build`
- [ ] مراجعة المستخدمين: عطّل حسابات من ترك الشركة، وراجع الأدوار
- [ ] تنظيف صور Docker القديمة: `docker image prune -f`
- [ ] مراجعة تحديثات الحزم الأمنية في GitHub ← Security ← Dependabot (فعّله من Settings ← Code security)

## كل 3 أشهر

- [ ] تحديث الحزم: `npm outdated` ثم تحديث في فرع مستقل، وCI يجب أن يكون أخضر قبل الدمج
- [ ] اختبار الأداء من جديد `npm run loadtest`. إن تجاوز p95 ثانية: كبّر الخادم أو راجع الاستعلامات البطيئة
- [ ] مراجعة حجم قاعدة البيانات: `docker compose exec db psql -U erp -c "select pg_size_pretty(pg_database_size('erp'))"`
- [ ] مراجعة صلاحيات GitHub: من يملك حق الدفع إلى `main`، ومن يرى أسرار Actions

## سنويا

- [ ] تدوير الأسرار: `SESSION_SECRET` (يُخرج كل المستخدمين ويطلب دخولا جديدا)، ومفتاح Claude، ومفاتيح SSH للنشر ([الطريقة](RUNBOOK.md#تدوير-الأسرار))
- [ ] ترقية PostgreSQL إن قارب الإصدار نهاية دعمه (PostgreSQL 16 مدعوم حتى نوفمبر 2028)
- [ ] ترقية Ubuntu إلى LTS التالي إن قارب نهاية دعمه، بعد نسخة احتياطية كاملة للخادم من لوحة المزود
- [ ] مراجعة خطة الطوارئ: هل ما زالت أرقام وأسماء المسؤولين صحيحة؟

## عند كل تعديل على الكود

1. التعديل في فرع مستقل، وPull Request إلى `main`.
2. إن تغيّر `prisma/schema.prisma`: أنشئ هجرة `npm run db:migrate -- --name وصف-التعديل` وارفعها مع الكود. CI يفشل إن تغير النموذج بلا هجرة.
3. الهجرات التي تحذف عمودا أو جدولا: قسّمها على نشرين (أولا توقف الكود عن استخدامه، ثم احذفه)، وخذ نسخة احتياطية يدوية قبلها.
4. الدمج بعد CI أخضر، والنشر التلقائي يتولى الباقي ويأخذ نسخة احتياطية قبل كل نشر.

## أهداف الخدمة

| المؤشر | الهدف |
| --- | --- |
| التوفر | 99.5% شهريا (حوالي 3.5 ساعات توقف كحد أقصى) |
| أقصى فقد بيانات مقبول (RPO) | 24 ساعة (النسخة اليومية). للتقليل: نسختان يوميا أو قاعدة مُدارة بنسخ مستمر |
| أقصى زمن للاستعادة (RTO) | ساعتان على خادم جديد |
| زمن الاستجابة | p95 أقل من ثانية |

## تحسينات مقترحة لاحقا

- تحويل المبالغ من `Float` إلى `Decimal` في قاعدة البيانات لدقة محاسبية كاملة (يحتاج هجرة واختبارات على الحسابات).
- قاعدة PostgreSQL مُدارة (DigitalOcean Managed Database أو ما يماثلها) عند نمو البيانات: نسخ مستمر واستعادة لأي لحظة.
- تجميع السجلات في خدمة خارجية (Better Stack أو Grafana Cloud) للبحث فيها بدل `docker compose logs`.
